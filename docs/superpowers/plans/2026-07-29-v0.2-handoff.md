## Hard rules

1. **TDD where the plan specifies it.** Write the failing test, run it, confirm it
   fails for the expected reason, then implement. Your report must contain the
   actual RED output, not a claim that it failed.
2. **`npm run validate` must pass before every commit.** It runs typecheck,
   Vitest, and the production build.
3. **Imports are extensionless.** `from './atmosphere'`, never
   `from './atmosphere.ts'`.
4. **Three.js stays pinned at `0.165.0`.** No dependency additions, removals, or
   upgrades. `dependencies` in `package.json` must be byte-identical at the end of
   your batch, except for the version bump in Task 8.
5. **Do not attempt the excluded optimisations.** The plan lists two — reducing
   the deformation FBO from 1024² to 512², and reducing terrain tessellation from
   256² to 128². Both degrade the carve trail, which is the feature the project
   exists to demonstrate, and neither is supported by measurement. If you think
   frame time demands them, say so in your report; do not act on it.
6. **The plan's code is the specification.** Use its exact values, names, and
   thresholds. Where the plan gives a complete code block, transcribe it — do not
   improve it. If you believe a block is wrong, stop and report rather than
   silently diverging.
7. **One commit per task**, using the commit message from that task's final step.
8. **Vitest never touches WebGL.** A GLSL error passes every unit test. Where a
   task has a browser verification step, actually run `npm run dev` and read the
   console. Report what you saw.

## When to stop and ask

Stop and report rather than guessing if:

- A step's code does not match the file on disk, and the difference is not
  explained by the uncommitted work listed above.
- A test fails for a reason the plan did not predict.
- A shader fails to compile.
- Two tasks in your batch want to change the same lines in incompatible ways.
- You find a defect in the plan itself.

Bad work is worse than no work. Escalating costs nothing.
